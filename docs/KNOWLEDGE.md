## K-01 官方约束转守卫 SOP

| 字段 | 值 |
|---|---|
| 类型 / 分类 | SOP / 验证 / DSH 插件开发 |
| 来源 | E-01、PRE-03、P-13、P-15 |
| Owner | AI Agent |
| 版本 / 更新频率 | 1.0 / 季度 |
| 适用场景 | 依赖外部框架契约的任何开发 |
| 边界条件 | 约束必须可被机器判定；纯风格约定不适用 |

**内容**

1. 通读契约（官方文档 + 装机实现 + 官方模板三源交叉）。
2. 把每条约束写成一句**可判定的断言**，而不是一条心得。
3. 在 `tools/verify-bundle.mjs` 中实现该断言。
4. **注入违规，确认守卫会失败**（见 K-04），再还原。
5. 把守卫加入 `npm run verify`。

**已落地的守卫（本轮真实产出）**

| 约束 | 守卫 |
|---|---|
| patch 行的 `name` 按包名引用，不得用裸子路径 | `no patch row uses a bare subpath` |
| 裸导入必须在 `peerDependencies` 中声明 | `every bare import is declared` |
| 资源必须用 `ctx.effect` 注册并可释放 | 测试「disposing the effect must release the route」 |
| 动作声明的参数必须真的影响命令行 | `tools/verify-params.mjs` |
| 工具行不得依赖 `webServer`（headless 保命） | 测试断言 `inject` 仅含 `tools` |

**量化效果**：本轮 7 条约束中 2 条「已读到但未遵守」，各导致 1 次返工（约 4–8 分钟＋1 轮重启）。转为守卫后该类缺陷逃逸率降为 0。

## K-02 三态可视设计规范

| 字段 | 值 |
|---|---|
| 类型 / 分类 | 规约 / 用户侧可观测性 |
| 来源 | E-02、SC-01、P-12 |
| Owner | AI Agent |
| 版本 / 更新频率 | 1.0 / 季度 |
| 适用场景 | 一切异步、可能失败的用户可见能力 |
| 边界条件 | 必须有可承载状态的 UI 位；纯后台能力改用日志或诊断路由 |

**内容**

任何异步能力必须区分三态，禁止「统一显示为空」：

| 态 | 含义 | 信号 |
|---|---|---|
| 正常值 | 拿到了数据 | 显示数据 |
| 合法空值 | 请求成功但没有内容 | 中性色占位（如 `—`） |
| 故障 | 请求失败或未注册 | 错误色（如 `!`）＋ 悬停写明原因 |

**判定标准**：非技术用户能否不问日志就说出「是坏了还是本来就没有」。

**已落地实例**：分支胶囊（0.4.0）。故障态用 `--dsw-alias-state-error-primary` 渲染 `!`，悬停文案为 `GitHub branch unavailable — route 404 (the Host route did not answer)`。

**量化效果**：故障定位轮次由 3 降至 1。本轮静默失败曾导致连续 3 轮无效诊断。

## K-04 守卫双向验证流程

| 字段 | 值 |
|---|---|
| 类型 / 分类 | 流程 / 质量门禁 |
| 来源 | E-04、PRE-06、P-17 |
| Owner | AI Agent |
| 版本 / 更新频率 | 1.0 / 半年 |
| 适用场景 | 任何新增或修改的守卫 |
| 边界条件 | 能构造违规样本；无法构造时应标注为【未验证】 |

**流程**

```
写守卫 → 注入违规 → 确认守卫失败 → 还原 → 确认守卫通过 → 记录两次结果
```

**为什么必须有**：本轮 3 个守卫中 1 个曾**恒真通过**（统计命令返回 0），1 个曾**误报注释**。守卫的单向验证等于没验证。

**已落地实例**

| 违规注入 | 结果 |
|---|---|
| 在 `verify-params` 覆盖范围外加一个死参数 `deadProbe` | 正确 FAIL |
| 描述里写不存在的动作名 `create/release-edit` | **首次未捕获**（正则不接受连字符，被静默降级为散文）→ 修正后正确 FAIL |
| `verify-bundle` 的 client 检查加注释干扰 | 修正后正确通过，去掉注释剥离则 FAIL |

**量化效果**：守卫可信度由「未知」变为「已证明」。第二行那次失败直接暴露了守卫自身的漏洞。

## K-05 逐动作实机探针 SOP

|---|---|
| 类型 / 分类 | SOP + 脚本 / 验证 / CLI 包装 |
| 来源 | E-05、PRE-02、P-01、P-02、P-05、P-06 |
| Owner | AI Agent |
| 版本 / 更新频率 | 1.0 / 月度 |
| 适用场景 | 任何包装外部命令行的工具 |
| 边界条件 | **仅只读动作**；写操作绝不执行 |

**内容**

1. 枚举工具的**全部只读动作**（本轮 58 个动作中 21 个只读）。
2. 为每个动作准备最小参数样本。
3. 通过**真实注册表**注册工具（`registerDomainTools`），而非直接调 argv。
4. 逐个 `execute`，捕获 `exitCode` 与 `stderr`/`stdout` 首行。
5. 匹配用法错误词表。
6. **断言「不是用法错误」而非「成功」**——任意资源探测本就会 404，网络失败也必须容忍。

**用法错误词表**

```
unknown flag | unknown command | unknown shorthand
| Unknown JSON field | unknown field | invalid search query
| accepts \d+ arg | required flag | invalid argument | Usage:\s+gh
```

**量化效果**：本轮由此发现 **5 个从未成功执行过一次**的动作（自 0.1.0 起）。离线套件 97 项全绿时它们依然全废。

**已落地**：`test/live-readonly.mjs`，已纳入 `npm run verify`。

## K-06 上游 CLI 支持面核验法

| 字段 | 值 |
|---|---|
| 类型 / 分类 | 检查表 / 侦察 |
| 来源 | E-06、PRE-01、P-02、P-05 |
| Owner | AI Agent |
| 版本 / 更新频率 | 1.0 / 季度 |
| 适用场景 | 包装任何外部 CLI 之前 |
| 边界条件 | CLI 可执行；无法执行时标注【待验证】 |

**检查表**

- [ ] `gh <cmd> --help` 是否真的列出这个标志？
- [ ] 该子命令的 `--json` 字段名是否与其他子命令**不同**？
- [ ] 布尔标志在 argv 中占 1 个元素还是带值？
- [ ] 位置参数中带空格的查询需要如何切分？

**实测结论（gh 2.89.0）**

| 事实 | 证据 |
|---|---|
| `gh api` **没有** `--json` | 加 `--json` 报 `unknown flag: --json` |
| `gh search commits --json` 无扁平 `message`/`committedDate` | 主题在 `commit`，日期在 `committer` |
| `gh search repos` 词表与 `gh repo list` **不可互换** | `fullName`/`stargazersCount`/`language` vs `nameWithOwner`/`stargazerCount`/`primaryLanguage` |
| 分支名中的斜杠必须**原样**插入路径 | `af%2F123` → 404；`af/123` → 200 |
| `gh release edit --latest` 存在 | `--help` 实测 |

**量化效果**：本轮 6 个缺陷同源。核验一条 `--help` 的成本约 1 秒，返工一轮约 5 分钟。

## K-07 参数分类表模式

| 字段 | 值 |
|---|---|
| 类型 / 分类 | 模式 / 设计 |
| 来源 | E-07、P-03 |
| Owner | AI Agent |
| 版本 / 更新频率 | 1.0 / 半年 |
| 适用场景 | 参数分类、路由表、权限表等「按名推断」易错的场合 |
| 边界条件 | 分类规则可枚举 |

**模式**：把分类**显式写成一张表**，而不是按参数名推断。

**实例**：本项目曾按名字判断「哪个参数是 git ref」，而 `ref` 一词两义——`github_actions dispatch` 的 `ref` 是 git ref，`github_auth` 的 `ref` 是凭据引用。改为显式表 `REF_PARAMS`（11 对 (action, param)）并加交叉校验测试。

**另一实例**：参数描述的「动作前缀」必须用**真实动作 id**。`workflow list/view/dispatch` 看似清楚，机器无法映射到 `workflowList`/`workflowView`/`dispatch`，且掩盖了 `list` 也读取该参数的事实。现由 `verify-params` 强制。

**量化效果**：误分类风险由「随参数名扩散」降为 0。

2. 读其 `package.json` 与关键实现，**尤其是 manifest 声明**。
3. 对照差异，吸收**经证实有效**的部分。

| 发现 | 采用 |

<a id="k-12"></a>
## K-12 DSH UI 半身接入要点

| 字段 | 值 |
|---|---|
| 类型 / 分类 | 案例库 / DSH 插件 |
| 来源 | P-12、P-13、P-14、P-15（0.3.x–0.4.0 客户端半身实践） |
| Owner | AI Agent |
| 版本 / 更新频率 | 1.0 / 季度 |
| 适用场景 | 为 DSH 插件添加浏览器半身 |
| 边界条件 | **已安装 bundle**（非运行时定义的插件，两者路径不同） |

**要点**

1. **manifest**：`exports["./client"]` + `dsh.client = { platform:'web', immediately:true, inject:['@deepseek-ai/dsh-client-ui-conversation'] }`。
2. **入口形态**：`window.__ModuleLoader__.load({ id: <包名>, factory(require){…} })`。
   `id` 必须等于包名。这是**队列注册**，不是 ESM，`factory` 只拿到 `require`。
3. **无 JSX**；React 经 `require('react')` 取得。
   `styles` / `console` / `host` 只属于**求值路径**，脚本路径没有。
4. **样式**：组件内渲染 `<style>`；只用 `--dsw-*` 主题 token；**禁止** `require('@deepseek-ai/dsh-client-ui-primitives')`。
5. **数据通道**：已安装 bundle 没有 `host.call`，必须由 host 注册 `webServer` 路由，客户端 `fetch`。
6. **host 侧注册必须在 `ctx.effect` 内**，否则插件销毁不释放路由，下次激活报
   `webserver: duplicate exact route`。
7. **命名路由默认公开**，必须接 `connection.requestRejection`，否则绕过宿主鉴权。
8. **`webServer` 的获取**：`inject` 声明是硬依赖（headless 会整体不激活）；改用
   `ctx.on('internal/service')` 监听，兼顾两者。
9. **patch 行按包名引用**，裸子路径解析不到。

**量化效果**：该链路本轮共修复 4 个缺陷（路由时序、路由泄漏、鉴权缺口、子路径行）。

<a id="k-13"></a>
## K-13 连通性探针模式

| 字段 | 值 |
|---|---|
| 类型 / 分类 | 模式 / 可观测性 / 外部依赖 |
| 来源 | E-02、SC-01、P-01 |
| Owner | AI Agent |
| 版本 / 更新频率 | 1.0 / 季度 |
| 适用场景 | 一切依赖外部可执行文件或网络的能力 |
| 边界条件 | 能逐层分解出可独立执行的检查；层数不宜超过 6 |

**模式**

不要只报告「配置了什么」，要报告「现在什么能用」。把整条路径拆成一条**逐层隔离、逐层计时**的梯子，
任一层失败都不终止后续层。

| 规则 | 理由 |
|---|---|
| **任一层失败都不 abort** | 目的是显示「走到了哪一步」；在第一处失败就中止是可耻的 |
| **抛异常的层被捕获为该层失败** | 否则一个 throw 会把整条梯子变成一句无信息量的报错 |
| **整体判定跟随最后一公里** | 前几层全绿而末端失败，正是这个探针存在的理由 |
| **`recommended` 指名具体配置键或命令** | 「检查你的网络」不是建议 |
| **逐层计时** | 654 ms 的 `gh auth status` 和 0 ms 的进程内解析，故障含义完全不同 |

**反例（本项目实际发生过）**

`github_auth status` 报告 `gh installed: yes / authenticated: yes`，即「配置正确」；
但实际上一个动作都跑不通——**报告配置不等于报告可用**。

**另一处反例**：路由未注册时，界面渲染成与「正常无数据」完全相同的灰色破折号，
导致连续三轮无效诊断。探针把「哪一层断了」变成一句话。

**已落地**：`github_auth probe` + `tools/probe-connectivity.mjs`（19 项验证，分别驱动每层的失败）。

**量化效果**：外部依赖故障的定位由「多轮盲诊」降至一次调用；实测输出见 CHANGELOG 0.6.0。

<a id="k-14"></a>
## K-14 能力之外的组织层

| 字段 | 值 |
|---|---|
| 类型 / 分类 | 模式 / 插件设计 / 指导 |
| 来源 | E-01、E-02、U-02 |
| Owner | AI Agent |
| 版本 / 更新频率 | 1.0 / 季度 |
| 适用场景 | 提供能力（工具）的插件 |
| 边界条件 | 宿主提供 systemPrompt 或 skills 服务；否则只做工具 |

**模式**

工具回答「**能调用什么**」。它不回答「什么时候用哪个、按什么顺序、需要什么证据、什么时候该停、
能力不足时怎么办」。后者是独立的一层，缺了它，工具再好也会被误用。

**两个机制，分工明确**

| 机制 | 用途 | 成本 |
|---|---|---|
| `ctx.systemPrompt.section(...)` | 绝不能漏的规则 | **每一步都付费**——只写 schema 说不出来的 |
| `ctx.skills.register(...)` | 工作流 | 按需加载，可以长 |

**规则**

1. **能写进 schema 的不要写进提示词。** 提示词的每一行都在每一步消耗 token。
2. **每条规则必须点名一个工具或动作**，否则它是空话。这条由守卫强制。
3. **section 名不得占用宿主保留名**——同层重名会抛。取名前先读宿主的保留名表。
4. **order 要落在宿主为同类 section 划定的区间内**，而不是随手取一个数。
   官方的工具类 section 在 1000–3100 带；插件工具 section 应紧随其后。
5. **`getSectionOrder(name)` 只认宿主保留名**，对插件名返回 `undefined`，
   而**非有限 order 会抛**——插件必须自己给数字。
6. **每个技能都要有停止条件。** 不知道何时该停的 agent 会一直调用工具。
7. **指导层必须可观测。** section 在不在提示词里、技能在不在目录里，从外面完全看不见；
   把状态发布到已有的诊断通道，否则它会静默失败。

**两个机制，分工明确（2026-10-16 按生态惯例修正）**

| 机制 | 用途 | 成本 |
|---|---|---|
| `ctx.systemPrompt.section(...)` | 绝不能漏的规则 | **每一步都付费**——只写 schema 说不出来的 |
| `ctx.skills.registerProvider(...)` | 工作流 | 按需加载，可以长 |

**职业技能为什么用 provider 而不是 `register()`**（读参考实现后改的）

| 项 | `register()` | `registerProvider()` |
|---|---|---|
| 技能体 | 内联在 JS 里，激活时定型 | **每次 `get()` 从磁盘重读** |
| 改措辞 | 要改代码并重新激活 | 改文件即可 |
| 相对引用 | 无法解析 | **`resourceBase` 让 `scripts/` 可解析** |
| 排序 | 无 `rank` 字段 | **`rank` 显式表达优先级** |

**`rank` 约定**：project/user/custom 根在 **100–500**，**打包技能用 600**——
所以**用户自己写的同名技能胜出**。本地文件是比打包文件更具体的意图表达。

**一致性规则**：技能目录名、`SKILL.md` 的 `name`、目录项名**必须是同一个名字**。
三者不一致时拒绝该技能并告警——否则目录会提供一个名字、文件在别处，而没有东西会报告。
缺 `description` 的技能整体排除：目录页展示描述而不是正文。

**每个技能要写自己的写入边界**：全局规则说「破坏性动作会问用户」，
但**批准 PR、重跑 workflow、推送修复不是同一种许可**，边界因工作流而异。

**已落地**：`skills/<name>/SKILL.md` × 3 + `lib/skill-provider.js` +
`tools/probe-guidance.mjs`（66 项，**读真实文件**）+ 诊断路由的 `guidance` 字段。

**量化效果**：本地守卫发现 3 条规则没点名工具、1 处 front matter 不一致；双向验证另发现
守卫自身的模板字符串被 shell 吞掉。这些在激活时都不会报错，只会让指导层悄悄失效。

<a id="k-15"></a>
## K-15 第三方仓库安全侦察（先验证，再克隆，扫完即删）

| 字段 | 值 |
|---|---|
| 类型 / 分类 | SOP + 工具 / 供应链安全 / 调研 |
| 来源 | E-06、E-08、S-06 |
| Owner | AI Agent |
| 版本 / 更新频率 | 1.0 / 季度 |
| 适用场景 | 把任何第三方项目当作参考或依赖之前 |
| 边界条件 | 只读分析；绝不安装、构建或运行被克隆的代码 |

**为什么要这道闸门**

`git clone` 本身不执行仓库内容。**危险的是它之后发生的事**：`postinstall` 脚本、submodule
拉取的第二个仓库、Git LFS filter 调用的辅助程序、指向树外的符号链接。关键在于
**在代码还是远程的时候做判断**——那时拒绝是零成本的。

**三阶段，顺序不能换**

| 阶段 | 做什么 | 用什么 |
|---|---|---|
| **1 预检（不下载任何字节）** | 读元数据与文件树，找「会执行的东西」 | GitHub API |
| **2 克隆（关掉所有执行面）** | 浅克隆、单分支、无 tag、**无 submodule**、符号链接写成文本、跳过 LFS smudge、hooks 路径改道 | `git -c core.symlinks=false -c core.hooksPath=<空目录> clone --depth 1 --no-tags` |
| **3 扫描真实字节 + 清除** | **只读**扫描；然后彻底删除并独立复核 | 本工具 |

**预检清单**

- 元数据：大小（>200 MB 拒绝）、归档、禁用、fork、许可证、最后推送
- 执行面：`.gitmodules`／`.gitattributes`（`filter=`）／`binding.gyp`／`setup.py`／`install.sh`
- 逐字读取：`package.json` 的 `pre|post|install` 钩子、`.gitattributes` 的 filter 行
- **判级要克制**：有 `package.json` 只是 info，不是警告——几乎每个 JS 项目都有，
  全部报警会训练人无脑加 `--yes`

**扫描的告警模式**：安装钩子、`curl|sh`、`eval(fetch(...))`、读环境变量后外发、
读取凭据库、动态执行、超长 base64 块、postinstall 联网。

**已落地**：`tools/repo-recon.mjs`
（`--preflight` 只判断不下载 ／ `--keep` 保留供阅读 ／ `--purge` 彻底清除 ／ `--list` 现况）

**量化效果**：首次使用时对一个 ★2 的插件完成「预检 SAFE → 浅克隆 48 文件 → 无安装钩子、
无符号链接 → 读完真实实现 → 清除并独立复核无残留」全流程。
**读真实代码直接推翻了三条来自 README 的认知**（见 WORKFLOW.md §10）。---

<a id="k-16"></a>
## K-16 引用完整性扫描（改动影响面）

| 字段 | 值 |
|---|---|
| 类型 / 分类 | 检查表 / 验证 / 一致性 |
| 来源 | E-01、P-24 |
| Owner | AI Agent |
| 版本 / 更新频率 | 1.0 / 新增对外名称时 |
| 适用场景 | 改动任何会被别处引用的名称（工具名、动作名、版本号、路径）之后 |
| 边界条件 | 只校验**名称是否存在**，不校验语义是否正确；隐式引用（自然语言描述）不在覆盖范围 |

**问题**

改了一个对外名称，而**引用它的文本没改**。文本不会报错——它会**自信地叫模型去调一个不存在的东西**。

**与 P-24 是同一母因的两个方向**

| | 方向 | 表现 |
|---|---|---|
| P-24 | 守卫 → 被守卫对象 | 守卫读的是内存副本，原件变了它不知道 |
| K-16 | 被守卫对象 → 引用它的文本 | 原件变了，引用它的文本不知道 |

**两者都是「对象之间缺少连接」。** 守卫必须连到原件，文本必须连到注册表。

**做法：注册表从代码读出，不在守卫里重述**

重述的清单会与工具实际构建的清单分叉，而分叉在被发现之前不可见——这正是本文要防的。
`tools/probe-guidance.mjs` 动态 import `lib/domains/*.js`，收集 `tool` 与 `actions`。

**三种引用形态，一个解析器**

| 形态 | 例 | 处理 |
|---|---|---|
| 显式 | `` `github_pr` action `view` `` | 工具 + 动作都校验 |
| 多名 | `` `github_pr` action `merge`, `close` `` | 后续名字归同一个工具 |
| **裸的** | `` action `status` `` | 归到**同段落内最近的上文工具** |

**裸的那一种是关键**，也是不能用一个正则解决的原因：按「读者怎么读」来归属。
**同段落内没有上文工具时报告为「未归属」而不是猜**——猜会产生假警报，
而**会喊狼来了的守卫会被关掉**。

**双向验证（2026-10-16 实测）**

| 注入违规 | 结果 |
|---|---|
| `github_foo`（不存在的工具） | 拒绝，并列出全部真实工具 |
| `github_pr action nonexistentAction` | 拒绝，并列出该工具全部真实动作 |
| 把 `checks` 改成 `checkRuns` 但不改技能 | 拒绝——**影响面扫描要抓的正是这一条** |

**检查表**

- [ ] 新增/重命名工具或动作后，跑 `npm run probe:guidance`
- [ ] 守卫的注册表是**读出来的**，不是抄进去的
- [ ] 守卫能对**三种违规**分别失败
- [ ] 归属不明的引用**报告**而不是猜
